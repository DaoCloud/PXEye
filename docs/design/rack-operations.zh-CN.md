[English](rack-operations.md) · **简体中文** · [设计文档](README.zh-CN.md)

- 需求基线：[能力需求](rack-operations-requirements.zh-CN.md)。它描述目标能力的全貌；本文档说明其中每一项实际能做到什么。
- 状态：草案，第 8 节的事项待确认。记录已经决定和已经验证的内容。
- 事实依据：2026-11-19 在一个真实站点上读取 NICo Core 的接口定义并做只读调用。每个接口的请求和返回见[数据契约](rack-operations-data-contract.zh-CN.md)。
- 实现：站点开关 `rackOperations`，默认关闭。

## 1. 定位

在不影响装机的前提下，把已纳管设备的运行状态和机柜视角的信息做成运维人员用得上的页面。现阶段只读：帮人看清哪些设备没就绪、卡在哪一步、为什么，不发起会改变设备的操作。

装机和设备发现是产品主线。本方向不改它们的流程，只读取它们已有的数据并跳转到它们已有的入口。

## 2. 两类站点

NICo Core 对两类站点提供的数据差别很大，页面有没有内容取决于站点是哪一类。

| | 通用服务器站点 | 整机柜站点（GB200 一类） |
| --- | --- | --- |
| 服务器 | Core 有机器对象，数据齐全 | 同左 |
| 机柜 | 没有机柜对象，只有设备上人工声明的 `rack_id` | Core 有机柜对象、机柜组、机柜健康和机柜维护 |
| 交换机 | 接入交换机不由 Core 管理，只能从服务器的 LLDP 邻居看到 | Core 管理 NVLink 交换机 |
| 供电 | 机柜 PDU 不在 Core 里 | Core 管理供电框 |
| 槽位 | Core 不提供 | 对象上有槽位和托盘字段，来源未验证 |

验证用的站点是通用服务器站点。整机柜一列除服务器外都没有验证过，结论只来自接口定义。

## 3. 能力对照

十个功能域各自的目标、Core 实际提供什么、PXEye 做到哪一步，统一记录在[能力需求](rack-operations-requirements.zh-CN.md)第 6 节每个功能域下的“实现状态”里，只在那里维护。本文档只说明当前阶段的页面、规则和计划。

## 4. 页面

### 4.1 已完成

八个页面是“设备管理”下的二级菜单。服务器、交换机、供电框列出的就是设备管理里的设备，按类型分开，再加上 Core 回报的运行状态；告警汇总它们当前的健康告警；布线和发现诊断按交换机和 BMC 地址汇总；机柜列出 NICo 保存的机柜对象；操作记录列出 PXEye 发出的操作。

| 页面 | 目的 | 用户能做什么 | 验证程度 |
| --- | --- | --- | --- |
| 服务器 | 看出哪些服务器没就绪、卡在哪一步、为什么；核对上联交换机；发现没填机柜的设备 | 按“需要处理”和机柜筛选、搜索；打开运行状态（状态原因、健康告警、硬件能力、LLDP 邻居、状态时间线、固件清单）；跳到安装任务、硬件详情、地址管理；给没填机柜的设备打开系统配置填写；导入 U 位（“导入 U 位”） | 列表和运行状态的基本内容已用真实数据验证；状态时间线和固件清单按真实站点记录的返回结构实现，只用编写的示例数据验证过 |
| 交换机 | 查看 Core 管理的 NVLink 交换机的状态、健康、管理口和 Fabric Manager | 同上 | 只用编写的示例数据验证。通用服务器站点此页没有设备，显示适用范围说明 |
| 供电框 | 查看 Core 管理的供电框的状态、健康、容量和电压 | 同上 | 同上 |
| 告警 | 查看当前有哪些健康告警、影响了哪些服务器、交换机和供电框 | 按告警或按设备分组；按设备类型和分类筛选、搜索；看有多少告警带 `PreventAllocations`；打开设备的运行状态 | 只读取设备列表已返回的健康数据（没有新的 Core 接口）；只用编写的示例数据验证过 |
| 布线 | 按交换机查看每个服务器网口实际接到哪个端口；发现同一端口被多个网口报告的冲突；找出没有 LLDP 数据的服务器 | 按交换机筛选、搜索；打开服务器的硬件详情；导入交换机名称和面板端口名（“导入交换机信息”） | 数据来自服务器的 LLDP 邻居，结构已用真实数据验证（一台服务器、一台交换机）；页面只用编写的示例数据验证过。只展示实际观察到的连接，不和计划比对 |
| 发现诊断 | 查看 NICo 站点发现对每个 BMC 地址的探测结果，定位设备为什么没有被发现 | 按结果筛选、按地址/序列号/错误码搜索；失败的排在前面，显示错误码和处理建议；打开已关联设备的详情 | 返回结构已用真实数据验证（5 个地址，4 个连接被拒绝）；页面只用编写的示例数据验证过 |
| 机柜 | 查看 NICo 为声明的整机柜保存的机柜对象：机柜型号、状态、成员数量、状态和健康历史 | 打开机柜的历史；开启 `rackActions` 后发起或终止机柜维护、机柜固件更新 | 只用演示采集验证（一个 GB200 NVL72 机柜）；通用服务器站点没有机柜对象，页面会说明 |
| 操作记录 | 查看 PXEye 发出的每个操作，以及检查、结果和读回的状态 | 按操作和结果筛选；按对象 ID、序列号、名称、原因或操作者搜索；不能删除 | 只用演示采集和 `tools/core-replay.py --demo-writes` 验证 |

`rackActions` 关闭时，页面不向 NICo 发起写操作。开启后（同时 `rackOperations` 开启、不是只读观察实例），服务器、交换机、供电框页提供操作对话框（“操作”，或对最多 10 台选中设备的“批量操作”），机柜页提供机柜操作；规则见[操作类功能规则](rack-operations-actions.zh-CN.md)。有两个页面拥有由 PXEye 存在自己数据库里的数据，用 CSV 导入，从不写入 NICo；只读观察实例不提供这两项导入：

- 服务器页拥有 U 位（`serial,rack,unit[,height]`）。服务器列表显示 `U<n>`（高度大于 1 时显示 `U<n>–U<m>`）；机柜拓扑中，一个计算托盘区里每台服务器都有 U 位且不在编辑布局时，按 U 位从上到下排列。导入中的机柜列只与设备的机柜比对。
- 布线页拥有交换机信息（交换机和面板端口，按机箱 MAC 和端口与 LLDP 对应）。页面在 LLDP 报告的内容旁显示导入的名称。

格式、校验和对应规则见[数据契约](rack-operations-data-contract.zh-CN.md)。

服务器的运行状态在打开后另外读取四项，各自显示读取中、结果或失败，不影响弹窗的其他内容：

| 内容 | 用途 | 说明 |
| --- | --- | --- |
| 状态时间线 | 一台机器经历了哪些状态、各停留多久，当前停在哪一步 | 连续相同的状态合并为一段；最后一段算到读取时 |
| 固件清单 | 各部件的实际固件版本，以及机型、部件号、锁定状态、安全启动 | 只展示版本，不判断是否合规（没有主机固件基线）；列表上不逐行读取 |
| 健康历史 | 这台机器出过哪些告警、从何时开始、最后出现在何时、是否已恢复 | 同一告警消失后再出现，算作两段 |
| 硬件校验 | 校验记录、每次的结果和各测试项的结果 | 验证站点只有一次“已跳过”的记录；测试项结果的字段只来自接口定义 |

### 4.4 不做或做不了

- 机柜功率汇总：Core 不返回功率读数，要做只能接 PDU。
- 插口级供电管理：Core 的供电框没有插口。
- 泄漏检测联动：Core 没有专门接口。
- 第三方交换机的端口和配置：不由 Core 管理。
- 交换机系统安装、DPU 升级、固件基线：已明确暂不做。经 NICo 的单次组件固件更新在 `rackActions` 下已有。
- 到货计划：已明确暂缓。设备管理的“设备规划”已有按序列号导入和比对，届时在它上面扩展。

## 5. 设计规则

通用规则见[交互规则](interaction-rules.zh-CN.md)。本方向另外约定：

1. 先只读。
2. 不改装机和设备发现；新功能放在新文件里，公共文件只加注册。
2. 开关关闭时导航和接口与原来一致。
4. 设备清单用设备管理的那一份，按 Core 的对象标识关联，不另建设备数据。
5. 详情、地址、机柜填写都跳转到现有弹窗。
6. 只展示有数据的内容。
7. “需要处理”用 Core 自己的信号：状态机处理失败、超出状态时限或有健康告警。
8. 这些页面唯一可编辑的数据是 PXEye 本地数据：U 位和交换机信息。它们只用于显示和比对，不写入 NICo，只读观察实例上不能编辑。

## 6. 操作类功能的前提

操作类功能已在 `rackActions` 开关下实现，没有在站点验证。操作、对应的 NICo 接口、是否需要 RMS、与装机的避让、确认、执行、审计以及 NICo 不提供的操作见[操作类功能规则](rack-operations-actions.zh-CN.md)；各领域的实现状态见[能力需求](rack-operations-requirements.zh-CN.md)。

仍待解决：

- 验证：一个可写的测试环境和指定设备；需要 RMS 的操作还要部署 RMS。
- 安装预检还没有读取操作记录；这是受保护的安装代码，要单独评审。
- 操作者身份：记录里只有会话和来源地址。

## 7. 开发方式

- 用一个只读观察实例接真实数据：同一个镜像，开启 `readOnly`，连接现有站点的 Core。它拒绝一切写请求，不参与装机，可以和正在使用的控制台并存。
- 到站点后按[现场采集指南](../field-survey/README.zh-CN.md)逐页采集：用哪些命令行和接口、怎么核对、需要用户补充什么。
- 离开站点后用采集文件回放（`tools/core-replay.py`）开发和测试，不再手写 Core 的返回。
- 站点的原始返回数据和操作记录不进入本仓库。
