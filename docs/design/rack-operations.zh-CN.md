# 机柜运维：范围与现状

[English](rack-operations.md) · **简体中文** · [设计文档](README.zh-CN.md)

- 状态：草案，第 8 节的事项待确认。记录已经决定和已经验证的内容。
- 事实依据：2026-11-19 在一个真实站点上读取 NICo Core 的接口定义并做只读调用。每个接口的请求和返回见[数据契约](rack-operations-data-contract.zh-CN.md)。
- 实现：站点开关 `rackOperations`，默认关闭。

## 1. 定位

在不影响装机的前提下，把已纳管设备的运行状态和机柜视角的信息做成运维人员用得上的页面。现阶段只读：帮人看清哪些设备没就绪、卡在哪一步、为什么，不发起会改变设备的操作。

装机和设备发现是产品主线。本方向不改它们的流程，只读取它们已有的数据并跳转到它们已有的入口。

## 2. 两类站点

NICo Core 对两类站点提供的数据差别很大，页面有没有内容取决于站点是哪一类。

| | 通用服务器站点 | 整机柜站点（GB200 一类） |
| --- | --- | --- |
| 服务器 | Core 有机器对象，数据齐全 | 同左 |
| 机柜 | 没有机柜对象，只有设备上人工声明的 `rack_id` | Core 有机柜对象、机柜组、机柜健康和机柜维护 |
| 交换机 | 接入交换机不由 Core 管理，只能从服务器的 LLDP 邻居看到 | Core 管理 NVLink 交换机 |
| 供电 | 机柜 PDU 不在 Core 里 | Core 管理供电框 |
| 槽位 | Core 不提供 | 对象上有槽位和托盘字段，来源未验证 |

验证用的站点是通用服务器站点。整机柜一列除服务器外都没有验证过，结论只来自接口定义。

## 3. 能力对照

按机柜级管理通常包含的十类能力，逐项说明 Core 实际提供什么、PXEye 做到哪一步。

| 能力 | Core 实际提供 | PXEye 现状 | 结论 |
| --- | --- | --- | --- |
| 机柜与资产 | 设备清单、序列号、人工声明的 `rack_id`；机柜对象只在整机柜站点有；没有 U 位 | 设备管理和机柜拓扑已有；排列顺序由 PXEye 保存 | 已有。U 位如需要只能自己记录。没有变更审计 |
| 拓扑与连接 | 服务器的 LLDP 邻居，含对端交换机名、型号、序列号（已验证）；网络拓扑接口返回空 | 服务器页显示上联交换机，运行状态里列出全部邻居 | 查看已做。预期与实际的比对未做，缺少预期布线作基准 |
| 电源与操作编排 | 电源的期望和实际状态；有上下电和复位接口；机柜级编排只面向整机柜；没有功率读数 | 只显示电源状态 | 操作未做。功率汇总从 Core 做不出来 |
| 固件 | 每台机器的固件清单、锁定状态、安全启动状态（已验证）；有更新接口；验证站点没有主机固件基线 | 未展示 | 固件清单列为下一步。合规判断缺基线。更新未做 |
| 装机与启动 | 产品主线 | 已有 | 不在本方向内 |
| 网络与互联 | 网段、VPC、InfiniBand、NVLink 分区接口存在 | 网络管理只覆盖装机用的网段 | 本方向不涉及 |
| 监控与健康 | 每个对象的健康告警和健康历史（已验证）；没有时序指标；没有泄漏或液冷的专门接口 | 服务器页显示健康和告警 | 单设备健康已做。告警汇总和历史未做。曲线要另接监控系统 |
| 安全与可信 | 有证明和度量相关的读取接口 | 未涉及 | 未调查，本阶段不做 |
| 交付、释放与复用 | 实例管理 | 已有 | 不在本方向内 |
| 故障、维修与退役 | 隔离、维护标记、机器校验、SKU、退役接口存在；验证站点的校验被跳过、没有 SKU | 运行状态里显示隔离和维护标记 | 查看部分已做。操作未做 |

## 4. 页面

### 4.1 已完成

三个页面是“设备管理”下的二级菜单。它们列出的就是设备管理里的设备，按类型分开，再加上 Core 回报的运行状态。

| 页面 | 目的 | 用户能做什么 | 验证程度 |
| --- | --- | --- | --- |
| 服务器 | 看出哪些服务器没就绪、卡在哪一步、为什么；核对上联交换机；发现没填机柜的设备 | 按“需要处理”和机柜筛选、搜索；打开运行状态（状态原因、健康告警、硬件能力、LLDP 邻居）；跳到安装任务、硬件详情、地址管理；给没填机柜的设备打开系统配置填写 | 已用真实数据验证 |
| 交换机 | 查看 Core 管理的 NVLink 交换机的状态、健康、管理口和 Fabric Manager | 同上 | 只用编写的示例数据验证。通用服务器站点此页没有设备，显示适用范围说明 |
| 供电框 | 查看 Core 管理的供电框的状态、健康、容量和电压 | 同上 | 同上 |

页面不发起写操作。

### 4.2 下一步

验证站点上有真实数据，加在服务器的运行状态里，不新开页面。

| 内容 | 用途 |
| --- | --- |
| 机器状态时间线 | 一台机器经历了哪些状态、各停留多久 |
| 固件清单 | 各部件的实际固件版本，装机前发现版本不齐 |

### 4.3 候选

| 内容 | 要先决定的事 |
| --- | --- |
| 发现诊断（探测失败的地址、错误码和处理建议） | 和设备管理“发现设备”页签的关系 |
| 健康历史、告警汇总 | 是否值得单独成页 |
| 硬件校验 | 站点是否启用机器校验或 SKU |
| 布线校验 | 预期布线从哪里来 |

### 4.4 不做或做不了

- 机柜功率汇总：Core 不返回功率读数，要做只能接 PDU。
- 插口级供电管理：Core 的供电框没有插口。
- 泄漏检测联动：Core 没有专门接口。
- 第三方交换机的端口和配置：不由 Core 管理。
- 交换机系统安装、DPU 和固件升级：已明确暂不做。
- 到货计划：已明确暂缓。设备管理的“设备规划”已有按序列号导入和比对，届时在它上面扩展。

## 5. 设计规则

通用规则见[交互规则](interaction-rules.zh-CN.md)。本方向另外约定：

1. 先只读。
2. 不改装机和设备发现；新功能放在新文件里，公共文件只加注册。
3. 开关关闭时导航和接口与原来一致。
4. 设备清单用设备管理的那一份，按 Core 的对象标识关联，不另建设备数据。
5. 详情、地址、机柜填写都跳转到现有弹窗。
6. 只展示有数据的内容。
7. “需要处理”用 Core 自己的信号：状态机处理失败、超出状态时限或有健康告警。

## 6. 操作类功能的前提

Core 提供电源、维护、隔离、固件、校验、退役等操作接口。它们都没有集成，也没有验证过。开始之前要先定：

- 和装机的避让：设备有进行中的安装任务时是否一律拒绝。
- 确认方式：哪些操作需要二次确认，批量操作的上限。
- 审计：操作记录保存什么、存在哪里。
- 验证范围：先在指定的测试设备上做，不在装机批次进行时做。
- 机柜级操作：通用服务器站点没有机柜对象，整柜操作只能由 PXEye 把单机操作按机柜编排，顺序和间隔要自己定。

## 7. 开发方式

- 用一个只读观察实例接真实数据：同一个镜像，开启 `readOnly`，连接现有站点的 Core。它拒绝一切写请求，不参与装机，可以和正在使用的控制台并存。
- 新站点上先用 `tools/core-survey.py` 核对接口，再对照[数据契约](rack-operations-data-contract.zh-CN.md)第 5 节的清单。
- 站点的原始返回数据和操作记录不进入本仓库。
